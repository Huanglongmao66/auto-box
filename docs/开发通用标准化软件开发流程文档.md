# 开发通用标准化软件开发流程文档
## 一、流程设计核心约束（AI 开发必须遵守）

1. 质量左移：需求、设计、安全、校验全部前置，禁止编码完成后统一排查问题

2. 阶段门禁：每阶段设置强制准入 / 退出标准，不达标禁止流转下一环节

3. 全链路可追溯：需求、代码、缺陷、变更、上线操作全部留存记录

4. 分团队适配：内置完整版（中大型项目）、轻量化版（3\-8 人小团队）、合规强管控版（政务 / 金融）三套分支流程，按需切换

5. 自动化优先：所有重复校验、构建、部署、测试交由流水线自动执行，减少人工操作

## 二、完整版企业级全流程（AI 开发标准执行模板）

### 阶段 1：需求阶段

#### 1\.1 需求收集

输入物料：客户业务文档、用户反馈、竞品分析、运营诉求、历史线上缺陷
输出物料：原始需求清单
执行动作：梳理全部干系人诉求，区分刚需功能、次要功能、远期规划预研功能

#### 1\.2 需求拆解

统一标准用户故事模板：作为 \[用户角色\]，我需要 \[功能行为\]，以达成 \[业务目标\]
配套输出：功能原型图、每条需求配套明确验收标准（可量化、可验证）

#### 1\.3 需求评审（强制门禁）

参会角色：产品、前端、后端、测试、架构设计人员
评审校验项：业务逻辑闭环、边界场景覆盖、性能指标、数据安全要求、权限逻辑、验收标准完整性
评审产出：评审问题整改清单、定稿需求基线文档
门禁规则：未完成评审、存在未整改核心问题，禁止进入设计阶段

#### 1\.4 需求变更管控（核心约束）

基线定稿后所有修改必须提交《需求变更单》
变更单包含：变更内容、影响工时、排期风险、关联模块、风险等级
全部相关人员确认签字后更新需求基线，同步所有开发、测试人员；无变更单的需求修改一律不予开发

### 阶段 2：四层分层设计阶段（逐层评审，AI 开发分层输出）

#### 2\.1 UI/UX 交互设计

输出：高保真 UI、交互逻辑文档、异常页面规范（空数据、加载、报错、无权限）、多端适配规则
评审点：交互一致性、操作合理性、异常场景完整性

#### 2\.2 系统架构总体设计

输出：系统架构拓扑图、技术栈选型清单、中间件部署方案、服务拆分关系
非功能指标定义：并发承载量、接口最大响应时间、故障容灾策略、日志采集规范

#### 2\.3 数据库设计

输出：ER 实体关系图、完整数据表结构、索引配置、数据字典、分库分表规则、敏感字段加密存储方案
评审校验：字段冗余、索引性能、事务边界、数据备份策略

#### 2\.4 接口 \& 模块详细设计

后端输出：完整 API 文档（请求参数、返回参数、全局错误码、鉴权规则）
前端输出：路由规划、公共组件拆分、全局状态管理方案
门禁规则：架构、数据库、接口三份文档全部评审通过，方可启动编码

### 阶段 3：编码开发阶段（AI 代码生成适配规范）

#### 3\.1 开发环境与仓库前置规范

1. 代码仓库分支标准
main：线上稳定主干，禁止直接提交代码
dev：迭代集成测试分支
feature / 任务 ID：单人功能开发分支
bugfix / 缺陷 ID：线上紧急修复分支
hotfix：重大故障紧急补丁分支

2. 统一基础规范：编码命名、注释标准、日志打印规范、错误码统一管理

3. 环境分层：本地开发环境 → 自动化测试环境 → 预发布环境 → 生产环境

#### 3\.2 AI 辅助编码完整流程

1. 开发领取需求任务，创建独立 feature 分支

2. AI 生成代码后人工本地自检：单元测试编写、接口本地联调、边界用例自测

3. 提交 MR/PR 合并请求，流水线自动执行 CI 校验：代码格式化、静态漏洞扫描、单元测试执行、语法校验

4. 人工 CR 代码评审：至少 1 人审核逻辑漏洞、性能隐患、安全风险（明文密码、SQL 拼接、越权漏洞等）
门禁规则：CI 流水线失败、CR 未通过、单元测试覆盖率不达标（核心模块≥80%），禁止合并至 dev 分支

5. 合并完成后流水线自动部署至测试环境

#### 3\.3 编码强制禁令（AI 生成代码必须过滤）

禁止硬编码配置、明文存储密钥、原生 SQL 字符串拼接、无权限校验接口、未捕获异常裸抛出

### 阶段 4：分层测试流程（自动化 \+ 人工双重校验）

1. 单元测试：开发 / AI 生成，最小函数、接口粒度验证，CI 自动运行

2. 接口自动化测试：全接口场景用例，代码合并自动批量执行

3. 功能黑盒测试：基于需求验收标准覆盖正常流程、异常流程、边界值、权限校验

4. 专项测试（中大型项目强制）
性能测试：并发压测、接口耗时、数据库负载检测
安全测试：XSS、SQL 注入、水平 / 垂直越权、敏感信息泄露扫描
兼容性测试：多终端、多版本系统适配

5. 缺陷分级管控
致命 / 严重缺陷：阻塞上线，必须全部修复并复测关闭
一般 / 轻微缺陷：可记录归档，非阻塞上线，但需排期修复
门禁规则：存在未关闭致命 / 严重缺陷，禁止进入预发布阶段

### 阶段 5：预发布与灰度上线阶段

#### 5\.1 UAT 预发布验证

预发布环境配置 1:1 复刻生产，导入脱敏生产副本数据
执行全流程完整回归测试；产品、客户完成用户验收测试，签署上线确认单

#### 5\.2 上线方案前置输出

上线操作步骤、一键回滚脚本、故障停机窗口、各环节负责人、线上风险应急预案

#### 5\.3 灰度发布流程

10% 流量灰度验证 → 持续监控 30 分钟无异常 → 50% 流量放量 → 全量发布
监控指标：接口报错率、接口平均响应时间、服务器负载、用户异常反馈

#### 5\.4 故障处理规则

灰度 / 全量上线出现致命故障，立即执行回滚脚本，恢复上一稳定版本，同步记录线上故障报告
上线完成同步通知运维、客服、运营团队

### 阶段 6：线上运维监控保障

1. 实时监控体系：业务日志、服务状态、数据库指标、异常告警机器人推送

2. 线上缺陷闭环流程：紧急 bug 创建 bugfix 分支，快速修复、灰度验证、上线

3. 周期性运维：定时全量数据备份、服务器巡检、账号权限定期清理

### 阶段 7：迭代复盘与资产归档

1. 版本上线 3 个工作日内迭代复盘会
复盘维度：需求变更问题、开发延期原因、测试漏测场景、线上故障、流程低效卡点
输出：流程优化整改项，更新下一轮开发规范

2. 项目资产统一归档：需求文档、设计图纸、接口文档、测试用例、版本包、上线记录、故障报告

3. 复盘完成后启动下一轮需求排期循环

## 三、两套轻量化适配模板（AI 按需选用）

### 轻量化小团队流程（3\-8 人小型工具 / 初创项目）

1. 需求：输出原型 \+ 简易验收标准，简化正式评审，全员快速同步沟通，简化变更单流程

2. 设计：取消独立架构评审，仅输出简易架构草图与核心数据表

3. 开发：简化分支体系（main/dev/feature），CR 简化为交叉快速核对，降低单元测试覆盖率要求

4. 测试：开发自测 \+ 一轮人工功能测试，上线前仅简易性能扫描，省略完整安全渗透

5. 发布：小流量灰度验证后直接全量上线，简化 UAT 签字流程

6. 复盘：每周 15 分钟简短同步，无需输出长篇复盘文档

### 强合规管控流程（政务、金融、等保要求项目）

在完整版流程基础上增加：

1. 需求阶段：法务合规评审、数据隐私专项评审

2. 设计阶段：安全架构独立评审、等保规范适配校验

3. 测试阶段：第三方专业安全渗透测试、数据脱敏专项测试

4. 上线阶段：多级变更审批、运维安全二次审核、全操作日志永久审计留存

5. 全流程：所有文档、评审记录、上线操作长期归档，满足监管审计要求

## 四、配套工具清单（AI 开发可直接集成）

需求项目管理：TAPD、飞书项目、Jira
原型设计：Figma、墨刀
代码与 CI/CD：GitLab/Gitee、Jenkins 自动化流水线
接口文档：Apifox、Swagger
测试工具：Postman、JUnit、Pytest 自动化框架
运维监控：Prometheus、Grafana、ELK 日志、企业微信告警机器人
知识库归档：飞书文档、Confluence

## 五、流程落地硬性门禁总表（AI 自动校验判断条件）

1. 需求未评审通过 → 禁止设计

2. 设计文档未评审通过 → 禁止编码

3. CI 流水线失败、代码未 CR、覆盖率不达标 → 禁止合并代码

4. 存在未修复致命 / 严重缺陷 → 禁止预发布验证

5. 未完成 UAT 验收、无上线回滚方案 → 禁止灰度上线

## 六、流程避坑约束（AI 开发全程遵守）

1. 禁止流程过度臃肿：小型项目强制使用轻量化分支流程，不照搬大厂多层评审

2. 禁止无基线随意变更需求：无变更单需求修改拒绝开发

3. 禁止测试后置：不允许全部编码完成后统一测试

4. 禁止上线无回滚预案：任何版本上线必须配套一键回滚脚本

5. 禁止省略代码评审：单人独立开发也需交叉代码核对

6. 禁止项目文档缺失：所有产出物统一归档，避免人员交接断层
